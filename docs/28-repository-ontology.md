# Repository Ontology

This is a descriptive ontology of Project Copperfin as the repository actually exists today: the concepts/entities present, how they relate, and where aspirational architecture docs (e.g. `docs/02-architecture.md`'s `copperfin-*` module list) diverge from what is actually built (the `cf_*` CMake targets below). Generated by inspecting `CMakeLists.txt`, `src/`, `include/`, `apps/`, `vsix/`, and `tests/` directly rather than restating planning docs.

## 1. Top-level entity classes

| Class | Instances | Where |
|---|---|---|
| Native static libraries | `cf_localization`, `cf_security`, `cf_platform_profile`, `cf_vfp_assets`, `cf_design_model`, `cf_prg_analysis`, `cf_runtime_text`, `cf_xbase_runtime`, `cf_runtime_pipeline` | `CMakeLists.txt`, `src/*`, `include/copperfin/*` |
| Native executables ("hosts") | `copperfin_inspect`, `copperfin_studio_host`, `copperfin_runtime_host`, `copperfin_build_host` | `apps/*/main.cpp` |
| Managed (.NET) projects | `Copperfin.VisualStudio` (VSIX), `Copperfin.Studio` (standalone shell), `Copperfin.DesignerSmokeTests`, `Copperfin.LanguageServiceTests` | `vsix/*` |
| VFP-era asset formats (domain data) | `DBF/FPT`, `CDX/DCX/IDX/MDX`, `DBC`, `PJX/PJT`, `SCX/SCT`, `VCX/VCT`, `FRX/FRT`, `LBX/LBT`, `MNX/MNT`, `PRG/H/QPR/MPR/SPR` | parsed/edited across `cf_vfp_assets`, `cf_design_model`, `cf_xbase_runtime` |
| Test suites | ~300 files under `tests/`, registered via `tests/CMakeLists.txt`, run through CTest | `tests/*` |
| Governance/process docs | `agents.md`, `agent-handoff.md`, `docs/01`…`docs/27`, `docs/safety/hazard-register.md` | repo root, `docs/` |

## 2. Native library dependency graph (ground truth, from `CMakeLists.txt`)

```
cf_localization                        (base: localization.cpp, no deps)
 ├─ cf_security                        (audit, auth, sha256, process hardening, secrets)
 ├─ cf_platform_profile                (database_model, extensibility_model, federation_execution, query_translator)
 ├─ cf_vfp_assets                      (DBF/CDX header+table readers, visual_asset_editor_*)
 └─ cf_runtime_text                    (runtime-scoped localized text)
      └─ cf_prg_analysis               (prg_engine_static_analysis.cpp)

cf_design_model  = cf_vfp_assets + cf_prg_analysis + cf_localization
                   (src/studio/*: designer_*, builder_*, toolbox_*, vs_launch_contract_*, report_layout, project_workspace, document_model)

cf_xbase_runtime = cf_prg_analysis + cf_runtime_text + cf_design_model(public) + cf_localization(private)
                   (src/runtime/prg_engine*.cpp + .inl, index_seek_optimizer, xasset_methods)

cf_runtime_pipeline = cf_design_model + cf_security + cf_platform_profile + cf_xbase_runtime
                   (src/runtime/runtime_pipeline_*.cpp — packaging, manifests, C#/launcher emission)
```

Executables consume this graph at the top:

```
copperfin_inspect      -> cf_vfp_assets, cf_security, cf_localization
copperfin_studio_host  -> cf_design_model, cf_security, cf_platform_profile
copperfin_runtime_host -> cf_xbase_runtime, cf_security, cf_platform_profile, cf_localization
copperfin_build_host   -> cf_runtime_pipeline, cf_localization
```

Note the inversion vs. the planning doc: `cf_design_model` (the "designer" concern) is a *dependency of* `cf_xbase_runtime` (the runtime engine), not the other way around — the runtime needs design-model types (e.g. extracted xAsset methods) to execute `SCX/VCX/MNX/FRX/LBX` startup assets.

## 3. Domain ontology — what each library models

### `cf_localization` / `cf_security` / `cf_platform_profile` (cross-cutting infrastructure)
- **Localization**: catalog-driven string lookup (`resources/locales/{en-US,es-419,pt-BR,qps-ploc}/strings.json`); each higher subsystem has its own `localized_text.{h,cpp}` shim over this base.
- **Security**: `authorization`, `audit_stream`, `external_process_policy`, `process_hardening`, `secret_provider`, `sha256` — an RBAC/audit/sandboxing layer (`docs/18-native-security-and-rbac.md`), independent of any one host.
- **Platform profile**: `database_model`, `query_translator`, `federation_execution`, `extensibility_model` — the "database federation" concept (`docs/21-database-federation-and-query-translation.md`): deterministic relational query translation plus AI-assisted document/vector planning metadata, surfaced into both Studio and the runtime host.

### `cf_vfp_assets` (file-format fidelity + visual asset editing)
- **Binary readers**: `dbf_header`, `dbf_table`, `cdx_header`, `index_probe`, `asset_inspector` — the DBF/FPT/CDX/index fidelity layer (Phase A, closed per `docs/02`).
- **Visual asset editor**: `visual_asset_editor_*` files — a round-trip-safe editor for `SCX/VCX/FRX/LBX/MNX` object models: property blobs, method blobs, object lifecycle, undo, and typed property setters split by concern (`appearance`, `behavior`, `data`). This is the engine behind safe in-place edits to legacy VFP visual assets without lossy rewrites.

### `cf_design_model` (designer/studio object model — *not* UI)
- **Document/project model**: `document_model`, `project_workspace`, `product_subsystems` (the "list VFP9-equivalent subsystems" feature), `report_layout` (FRX/LBX section model).
- **Designer surfaces**: `designer_context`, `designer_dispatch`, `designer_launch_surfaces`, `designer_invocation_admission` — admission-checked dispatch of designer actions.
- **Builders/Toolbox**: `builder_registry`, `builder_dispatch`, `builder_invocation_admission`, `toolbox_palette`, `toolbox_creation`, `toolbox_dispatch`, `toolbox_invocation_admission` — modeled equivalents of VFP's Builders and Toolbox.
- **Editor actions**: `editor_action_dispatch`, `context_editor_actions`, `editor_action_invocation_admission`.
- **VS launch contract**: `vs_launch_contract*` (largest single cluster, ~25 files) — the JSON request/response protocol consumed by `Copperfin.VisualStudio` and `Copperfin.Studio` to drive the native designer surfaces (selection, property get/set by appearance/behavior/data, object lifecycle, layout actions), each paired with a `*_validate.cpp`.

### `cf_xbase_runtime` (the PRG execution engine)
- `prg_engine.cpp` + a large family of `.inl` partials (`_dispatch`, `_flow`, `_expression`, `_records`, `_cursor`, `_arrays`, `_variables`, `_session`, `_sql`, `_aggregate`, `_dll`, `_free_functions`, `_index_seek`) — a single logical engine split across translation units (see `scripts/split_prg_engine.py`, evidence this was mechanically decomposed from one large file).
- Function-family modules: `_command_helpers`, `_date_time_functions`, `_file_io_functions`, `_numeric_functions`, `_path_functions`, `_string_functions`, `_type_functions`, `_table_structure_helpers`, `_runtime_surface_functions`, `_runtime_config` — VFP built-in function coverage, organized to mirror `docs/22-vfp-language-reference-coverage.md`.
- `index_seek_optimizer.cpp` — Rushmore-style seek/optimization logic (see `tests/test_prg_engine_rushmore_optimization.cpp`).
- `xasset_methods.cpp` — extracts dispatchable runtime actions (method invocations, menu selections) from `SCX/VCX/FRX/LBX/MNX` objects, the bridge that lets `cf_design_model` assets actually run.
- `prg_engine_static_analysis.cpp` (in the separate `cf_prg_analysis` target) — analysis that doesn't need the full runtime, kept as a lighter dependency for `cf_design_model`.

### `cf_runtime_pipeline` (build/package/debug orchestration)
- `runtime_pipeline_file_io_and_classification`, `_text_and_identifier_utils` — staging/classifying project assets.
- `_ast_ir_manifest`, `_fxp_and_archive_manifest`, `_library_export_manifest` — manifest generation for packaged output.
- `_csharp_and_launcher` — generates the `.NET` launcher stub (`docs/10-dotnet-interop.md` early modernization path).
- `_public_api` — the surface `copperfin_build_host` calls into.

## 4. Executable roles (the four native "hosts")

| Executable | Role | Key flags/behavior |
|---|---|---|
| `copperfin_inspect` | Low-level DBF/index inspector, no GUI | reads headers/records for diagnostics |
| `copperfin_studio_host` | Native backend for visual designers; emits JSON snapshots | `--json`, `--from-vs`, `--list-subsystems`; produces `reportLayout` for FRX/LBX |
| `copperfin_build_host` | Native packaging/build pipeline for `PJX/PJT` | `build --project ... --output-dir ... --enable-security --emit-dotnet-launcher`; writes `app.cfmanifest` |
| `copperfin_runtime_host` | Runtime + debugger host for packaged apps | reads `app.cfmanifest`, executes `PRG` startup via `cf_xbase_runtime`, supports breakpoints/step-debug, `--debug-command select:<id>` / `invoke:<id>` |

These four map 1:1 onto pipeline stages: `studio_host` (design-time) → `build_host` (package) → `runtime_host` (execute/debug), with `inspect` as a standalone diagnostic tool outside that pipeline.

## 5. Managed/.NET layer (`vsix/`)

- `Copperfin.VisualStudio` — VSIX package; hosts a "Copperfin Visual Designer" document shell for `PJX/SCX/VCX/FRX/LBX/MNX`, talks to `copperfin_studio_host`/`copperfin_runtime_host` over the JSON contract (`CopperfinStudioHostBridge`, `CopperfinRuntimeDebugClient`, `CopperfinProjectInsightClient`), plus a first-pass FoxPro language service (`FoxProCompletionSource`, `FoxProQuickInfoSource`, `FoxProSignatureHelpSource`) for `PRG/H/QPR/MPR/SPR`.
- `Copperfin.Studio` — standalone WinForms shell (`StudioMainForm`) reusing the same designer controls outside Visual Studio, now tabbed/multi-document.
- `Copperfin.DesignerSmokeTests` — WinForms smoke tests exercising real sample assets (`invoice.frx`, `cust.lbx`, `solution.pjx`) against the shared designer controls.
- `Copperfin.LanguageServiceTests` — tests for the FoxPro editor/language-service pieces.

Design rule stated in `docs/02-architecture.md`: the VS extension should *orchestrate* designers, not be their only implementation — consistent with the native `cf_design_model` + JSON contract split actually built.

## 6. Planned-but-not-yet-real layer (from `docs/02-architecture.md`)

The architecture doc names a `copperfin-*` module list (`copperfin-core`, `-data`, `-connectors`, `-runtime`, `-designer`, `-reports`, `-migrator`, `-dotnet`, `-gateway`, `-shield`, `-cli`, `-vsix`) and suggested submodules (`cf-dbf`, `cf-fpt`, `cf-cdx`, `cf-dbc`, `cf-repair`, `cf-sqlite`, `cf-postgres`, `cf-sqlserver`, `cf-oracle`, `cf_clr-host`, `cf-com-bridge`, etc.). **None of these exist as separate build targets today** — they are a target-state taxonomy, not current structure. The real `cf_*` targets in §2 are a flatter, more organically grown set that partially covers this taxonomy (mostly `-data`, `-designer`, `-runtime`, and slices of `-dotnet`/`-connectors` via `cf_platform_profile`); `-gateway`, `-shield` (beyond what `cf_security` covers), `-migrator`, and `-cli` have no dedicated code yet.

## 7. Process/governance ontology (non-code but load-bearing)

- **Issue hierarchy**: umbrella issues → parent/lane issues → prompt-sized child issues (only the last are execution units) — `agents.md`.
- **Execution status**: the ontology describes repository structure, not the active work queue. Current MVP workstreams and their completion gates live in `docs/05-roadmap.md`; issue-linked evidence lives in `agent-handoff.md` and progress documents.
- **Requirements Recovery**: a standing-but-deferred goal to build a DO-178-style requirement↔code↔test traceability matrix, grounded only in real installed VFP9 behavior or shipped docs (never decompiled binaries, per `docs/07-clean-room-rules.md`), with known-bug/crash exceptions tracked in `docs/27-known-vfp9-bug-exceptions.md`.
- **Safety documentation traceability**: `DQ-*`/`DV-*`/`HZ-*` identifiers link doc changes to `docs/safety/hazard-register.md` when operator-facing/procedural docs change.
- **Handoff contract**: `agent-handoff.md` (compact, current-state) vs. `remaining-work.md` (deprecated, do not use as a planning source) vs. `issues.txt` (local snapshot only, never authoritative over live GitHub issue state).

## 8. Cross-cutting relationships worth noting

- Every native library except the base `cf_localization` and `cf_runtime_text`/`cf_prg_analysis` pair depends on `cf_localization`, reflecting the hard localization-catalog requirement (`docs/26-localization-and-release-readiness.md`) — though per memory, actual call-site adoption is still thin outside these wired libraries.
- `cf_security` and `cf_platform_profile` are siblings consumed identically by both `copperfin_studio_host` and `copperfin_runtime_host`, but `copperfin_studio_host` does *not* link `cf_xbase_runtime` directly — design-time JSON snapshot generation doesn't need the execution engine, only `cf_design_model`.
- The VFP asset type taxonomy (§1) is the spine the whole ontology hangs off: each format has a reader in `cf_vfp_assets`, an editable object model in `cf_design_model`, and (for `SCX/VCX/MNX/FRX/LBX/PRG`) an executable surface in `cf_xbase_runtime`.
