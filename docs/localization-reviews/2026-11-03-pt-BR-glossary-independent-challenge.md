# Independent challenge of the pt-BR glossary proposal

**Scope:** read-only challenge of `docs/localization-reviews/2026-11-03-pt-BR-glossary-proposal-draft.md` against the current full-review source and pt-BR catalog. Reviewer: independent Codex agent `/root/review_en_gb_revisions`. AI linguistic judgment remains uncertain; no qualified human review, VFP UI run, or repository edit was performed.

| Proposal area | Verdict | Evidence and correction |
|---|---|---|
| Fixed tokens versus display text | **Accept.** | The builder registry localizes title/description/display equivalent while keeping `id`, `entry_point`, and `vfp9_equivalent` literal (`src/studio/builder_registry.cpp:52–101, 137–190`). Host JSON prints fixed `kind` values (`apps/copperfin_studio_host/studio_host_main_builder.cpp:402`). Preserve CLI flags, IDs, VFP property names, placeholders, enum values, and JSON field names exactly. |
| Wizard and Designer | **Accept provisionally.** | `Assistente` is natural for Wizard and already used by `Studio.Builder.LabelWizard.Title`; `Designer` matches product titles. Review explanatory sentences separately so “designer” is not flattened into “editor” when it names a product role. |
| Builder → Construtor everywhere | **Revise/defer.** | The registry has a distinct `builder` kind, IDs such as `class-builder`, and `cf_builders.class_builder` entry points (`src/studio/builder_registry.cpp:105–112, 137–190`). “Construtor de classes” can read as a class constructor, while current visible titles use `Builder de formulários` and `Builder de classes`. The source proves a VFP workflow category, not that “Construtor” is the preferred pt-BR UI term. Retain **Builder** in VFP-facing titles and diagnostics until a whole-family terminology test or authoritative VFP pt-BR UI reference supports changing it; never mix `Builder` and `Construtor` within the same surface. |
| Invocation/execution admission | **Accept concept, revise phrasing.** | `plan_studio_builder_invocation_admission` sets `ui_launch_admitted` and `dry_run` without execution (`src/studio/builder_invocation_admission.cpp:47–75`); execution readiness checks a separate `admit_execution` flag (`src/studio/builder_dispatch.cpp:50–83`). `autorização para invocar o Builder` and `autorização explícita para executar` are clearer than chains of genitives such as “autorização da invocação do construtor.” Keep the distinction between admission and completed execution. |
| Dispatch → encaminhamento | **Defer.** | The code builds a command argument plan (`src/studio/builder_dispatch.cpp:90–130`), then separately checks execution readiness. “Encaminhamento” may describe routing, but it does not establish the product term for `dispatch`; “despacho” is also viable. Choose one only after checking Builder, Designer, EditorAction, and Toolbox family sentences together. Do not globally replace `dispatch` in `IDispatch`, `Runtime.Prg.Dispatch`, tokens, or fields. |
| Launch plan / dry run | **Accept `simulação`; revise launch term.** | `dry_run` is a Boolean state distinct from execution, so `simulação` is sound in prose. `plano de inicialização` may suggest startup/boot rather than launching a Builder. Keep `plano de lançamento` provisionally or test `plano de acionamento` against surrounding UI before a global change. |
| VFP property labels | **Mostly defer as the author does.** | Setter code separates fixed property identifiers from localized diagnostic labels (`src/vfp/visual_asset_editor_property_setters_behavior.cpp:470–545`; `src/vfp/visual_asset_editor_property_setters_data.cpp:21–33`). `LockColumnsLeft` is a nonnegative count, so `número de colunas bloqueadas à esquerda` is justified. `KeyPreview`, `Sparse`, `PictureSelectionDisplay`, `LinkMaster`, and `IntegralHeight` require behavior evidence beyond setter types. In particular, `posição máxima à esquerda` for `MaxLeft` can imply the leftmost position; `posição esquerda máxima` is a closer coordinate label, pending bounds semantics. Preserve `KeyPreview`, `TABSTOP`, etc. in code/CLI. |
| Debugger action semantics | **Accept distinction, defer exact captions.** | `step_over` and `step_out` are separate runtime actions (`src/runtime/prg_engine.cpp:10487–10502`); do not use the same action verb for both. “Avançar sem entrar na chamada” and “sair da rotina” convey the distinction in descriptions. Compact buttons should be checked in the actual UI before replacing current captions. `expressões de inspeção` is plausible for Watch, but adopt it only for the entire watch tab/label/evaluation family. |
| Rushmore display | **Accept with narrower fallback wording.** | The host emits fixed `fallbackReason` and localized `fallbackReasonDisplay` separately (`apps/copperfin_studio_host/studio_host_main_rushmore.cpp:544–552`). Keep Rushmore and fixed enum strings. “Explicação do plano Rushmore” is sound. A fallback *reason* need not describe an alternate plan, so use `motivo do fallback` or `motivo da alternativa` provisionally rather than asserting `motivo do plano alternativo` for every enum. |
| Toolbox text labels | **Revise. Localize and keep current pt-BR values pending term polish.** | `print_text_toolbox_palette_*` calls `catalog.translate` on every `Text.Label.*`, whereas JSON emits fixed field names separately (`apps/copperfin_studio_host/studio_host_main_toolbox_palette.cpp:380–445, 448–522`). The pseudo-locale test explicitly rejects raw `toolbox_context:` in text mode (`tests/test_studio_host_json_parse_diagnostics_toolbox_palette.inl:70–84`). Current pt-BR and es-419 catalogs use locale-specific snake-case labels (`resources/locales/pt-BR/strings.json:592–610`). The draft's suggested switch to spaced labels is a separate output-format change and lacks compatibility evidence. The 19 batch-010 source-identical Toolbox labels must not revert to en-US; see `/tmp/copperfin-pt-batch010-source-identical-audit.md` for exact per-key dispositions. |
| Text `status: ok/error` freeze | **Revise. No blanket invariant.** | Rushmore text status is catalog-translated (`apps/copperfin_studio_host/studio_host_main_rushmore.cpp:556–564`), and `tests/test_studio_host_json_rushmore_explain.cpp:64–105` explicitly expects a pseudo-localized status. Toolbox text status is catalog-translated (`studio_host_main_toolbox_palette.cpp:448–506`); its JSON `"status": "error"` is fixed separately. Tests elsewhere that search `status: error` mostly exercise other hosts or default en-US; `tests/test_studio_host_json_parse_diagnostics_toolbox_palette.inl:48–84` checks en-US text plus pseudo-localized labels, not a pt-BR parser contract. Retain existing pt-BR `status: erro` and `status: sucesso` for the three batch-010 proposals; English `ok` can be an intentional pt-BR loanword in other keys only with an explicit per-key reason. |
| Security tier caveat | **Accept.** | Parsing, enum identity, and display text must be distinguished before freezing `bronze`, `silver`, or `gold`; description localization alone does not prove the tier tokens are fixed. |

## Release implication

The author correctly calls for a source-identity and consumer audit before changing potentially parsed output. The challenged text-mode families have direct evidence of localization, including a pseudo-locale test. Keep the 21 batch-010 source-identical pt-BR proposals held back, resolve Builder/dispatch terms family-wide, and add pt-BR text-mode assertions alongside existing JSON contract tests. This review is a terminology proposal, not approval of any catalog patch.
