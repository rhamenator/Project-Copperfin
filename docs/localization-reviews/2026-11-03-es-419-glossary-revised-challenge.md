# Independent challenge of revised es-419 glossary

**Reviewed:** `docs/localization-reviews/2026-11-03-es-419-glossary-revised-draft.md` against full-review checkout `d67afb2f1`, current `resources/locales/en-US/strings.json` and `resources/locales/es-419/strings.json`, prior `/tmp/copperfin-es-glossary-independent-review.md`, and available correction ledger files. **Overall decision: accept the terminology framework with the revisions below before it governs per-key approvals.** This is an independent AI/code review, not native-speaker or rendered-UI certification. No repository files changed. Batch 014 did not exist when this review began and was not reviewed here.

| Area | Verdict | Evidence and decision |
| --- | --- | --- |
| Protected tokens and Builder/Wizard/Designer | **Accept.** | `src/studio/builder_registry.cpp:105-150` keeps `builder`/`wizard` kinds, IDs, entry points and VFP equivalents separate from localized titles. Current es-419 already has `Studio.EditorAction.OpenBuilder.Label = Builder`, `Studio.Builder.FormBuilder.Title = Builder de formularios`, `Studio.Builder.MenuDesigner.Title = Diseñador de menús`, and `Studio.Builder.LabelWizard.Title = Asistente de etiquetas`. Use **Builder**, **asistente**, **diseñador** consistently for these product roles. Preserve `builder.app`, `ReportBuilder.app`, code identifiers, CLI flags, placeholders, and JSON keys exactly. Plural **Builders** is understandable but needs width/UI review. |
| Dispatch/admission model | **Accept distinction; revise several examples.** | `src/studio/builder_invocation_admission.cpp:47-75` records launch authorization and `dry_run`; `src/studio/builder_dispatch.cpp:50-125` prepares a dispatch after admission; execution has another explicit gate. **autorización para iniciar**, **autorización para ejecutar**, **preparación para iniciar**, and **envío para ejecutar** are suitable *where those actions occur*. In the proposed `A builder dispatch catalog request requires at least one context builder` example, “debe haber ... disponible” is weaker than the source's “requires at least one context builder”: the call at `builder_dispatch.cpp:150-165` fails when the admission catalog has no builder. Prefer “La solicitud del catálogo de preparación para iniciar Builders requiere al menos un Builder del contexto.” For `...non-executed dispatch`, “plan que aún no se haya ejecutado” is acceptable, but keep **plan de envío preparado** if another sentence needs to distinguish a launch plan from a dispatch plan. |
| Dry run wording | **Revise.** | “Ejecución simulada” is idiomatic, but the source sets `dry_run = !admit_ui_launch` and no UI launch occurs (`builder_invocation_admission.cpp:64-75`). The example “una invocación autorizada que no sea una ejecución simulada” can suggest that the invocation itself executed. Prefer “una invocación autorizada, sin el modo de simulación” or “una invocación autorizada que no sea una simulación”, with the latter checked against full sentence context. `--dry-run`, `dry_run`, and `dryRun` remain literal. “Use --dry-run para simular la ejecución sin iniciar el Builder” is a reasonable help sentence if that command actually exposes the flag. |
| Text-mode labels and status | **Accept conditional policy; extend it.** | `apps/copperfin_studio_host/studio_host_main_toolbox_palette.cpp:445-500` localizes text labels and status; JSON names remain fixed. `tests/test_studio_host_json_parse_diagnostics_toolbox_palette.inl:60-84` expects qps-ploc to decorate labels and reject raw `toolbox_context:`. Thus text labels are not universally source-identical. The glossary correctly avoids piecemeal changes to current `ruta_activo`, but its explicit decision must also include **status lines**: current es-419 `StudioHost.ToolboxPalette.Text.Status.Ok` and `StudioHost.RushmoreExplain.Status.Ok` are `estado: correcto`, whereas en-US is `status: ok`. Audit per-command text consumers and tests before choosing localized human text or a stable parseable text contract. If human text is the policy, readable `ruta del recurso` and `ejecución simulada` fit better than pseudo-machine `ruta_activo` and `simulacion`. JSON is the safer structured surface, but that is a recommendation, not evidence that no outside text scraper exists. |
| OLE and keyboard property labels | **Accept with semantic/width check.** | The VFP setters use fixed names (`TABSTOP` in `src/vfp/visual_asset_editor_property_setters_behavior.cpp:62-107`; OLE names in `src/vfp/visual_asset_editor_property_setters_appearance.cpp:88-110`) separately from localized labels. **recibe el foco con Tab** and **captura previa de teclas** avoid misleading tab-character/visual-preview readings. `OLEDropMode`/`OLEDropEffects` should remain exact only when an error names the API property. The glossary cites Microsoft .NET semantics and applies them to VFP by inference; verify VFP-specific behavior and actual label width before marking these keys approved. |
| Debugger terminology | **Accept with one phrasing adjustment.** | Current es-419 `AssetEditor.Debugger.Tab.Watches = Expresiones vigiladas` and `...EvaluatingWatchStatus = Evaluando expresión vigilada...`, so **expresión vigilada** is consistent. `src/runtime/prg_engine.cpp:8806-8836` evaluates watch expressions in a paused frame. The phrase **ventanas de expresiones vigiladas** may be long and can imply multiple app windows; where the source means the debugger feature rather than literal windows, prefer **vistas de expresiones vigiladas**. Preserve `watch` command/API names. |
| Rushmore and optimizer rationale | **Accept.** | `src/runtime/index_seek_optimizer.cpp:577-639` selects localized `match_reason` prose from heuristic score bands while the plan/strategy stays structured. **coincidencia de Rushmore de confianza alta/moderada** is clear; `Rushmore`, `AND`, enum values and SQL/VFP tokens remain literal. Verify that no consumer parses the localized rationale. |

## Before applying batch 014 or a family sweep

1. Review each proposed sentence against its exact en-US key and runtime branch. Do not transfer approval from this glossary to individual values. In particular, preserve whether a message refers to a launch plan, a dispatch plan, admission, or completed execution.
2. Verify exact source/current/proposal hashes and protected syntax per entry; compare with the existing es-419 correction ledger so accepted earlier keys are not silently replaced by an unreviewed glossary revision.
3. Resolve text-mode labels **and status** at the command level. Check en-US, es-419, and qps-ploc text/JSON behavior; record any fixed text contract explicitly.
4. Check VFP keyboard-property behavior and rendered UI width. AI wording review leaves these as residual uncertainty.
