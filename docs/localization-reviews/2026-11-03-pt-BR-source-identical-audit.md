# pt-BR batch 010 source-identical proposal audit

**Disposition:** revise all 21 accepted source-identical proposals. They replace existing localized pt-BR text with en-US text without a machine-contract need shown by these call sites. Retain the current pt-BR values listed below, subject to a later glossary and text-mode compatibility check. This is an AI-only read-only audit, not a qualified human linguistic review or runtime execution.

The host explicitly calls `catalog.translate` for the Rushmore text status (`apps/copperfin_studio_host/studio_host_main_rushmore.cpp:558–564`) and for toolbox text-mode status and labels (`apps/copperfin_studio_host/studio_host_main_toolbox_palette.cpp:448–522`). Its JSON branches emit fixed field names and status values independently (`studio_host_main_toolbox_palette.cpp:380–445`; `studio_host_main_rushmore.cpp:520–552`). `tests/test_studio_host_json_rushmore_explain.cpp:64–105` checks en-US text and a pseudo-localized Rushmore status, proving that status is routed through the catalog. Toolbox JSON tests assert fixed `dryRun`, `mutatesAsset`, `itemCount`, etc. (`tests/test_studio_host_json_dispatch_toolbox_palette_query_filters.inl:20–58`). I found no pt-BR text-mode assertion for these labels; add one before applying changes. Other tests asserting `status: error` mostly exercise default en-US or different hosts, so they do not prove these pt-BR keys must stay English.

The current pt-BR catalog already uses Portuguese snake-case labels (`resources/locales/pt-BR/strings.json:592–613`), and es-419 independently localizes the same label family. The snake-case shape is an output convention, not evidence that each English spelling is a machine key. External consumers could still scrape text mode; the compatibility question is about locale-dependent text-mode output as a whole, not a reason to silently revert just pt-BR to English.
